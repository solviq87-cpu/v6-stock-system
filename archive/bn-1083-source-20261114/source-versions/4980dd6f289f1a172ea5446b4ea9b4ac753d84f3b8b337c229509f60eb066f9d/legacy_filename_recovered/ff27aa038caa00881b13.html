维度你的选择

二、现状诊断（核查所得事实）

【事实】面板现有 9 大区块 + 30+ 子区块，全部「直接可见、纵向堆叠」；移动端只有 900px / 760px / 520px 三档断点，窄屏只做单列，没有针对手机的「内容精选」。
【事实】推送主通道为 飞书自定义机器人 webhook（open-apis/bot/v2/hook/<id>），当前 msg_type:'text' 纯文本；双机器人（公开群 + 私密）。有 feishuq.js 发送队列与 stripHtmlTags。
【事实】面板区块清单：①盘面总览 ②外围市场·选股核心 ③我的持仓 ④模拟盘 ⑤消息面 ⑥明日计划 ⑦我的十四条 ⑧复盘·学习 ⑨工具。首屏第 0 块为「📊 盘面总览」。

三、历史教训（为什么不能走「改布局」老路）

从代码版本注释链（APP_VER=20261017eb）可追溯到你过往四轮对「手机端折叠/置顶」的尝试：

轮次做了什么你的反馈

【结论】「折叠 / 置顶 / 吸顶」这条「改现有面板布局」的路，你已三次否决。 本方案的三条方向全部是 「新增」而非「改动」，彻底避开这个雷区。

四、优化方案（三个方向）

方向 A · 手机专属速览页 P0 最高优先级 最快见效

做什么：新增独立路由 /m，返回一个全新轻量页（完全不动 index.html），只放「一眼结论」，不放大表格。

页面内容（自上而下，一屏看完）：

  • 🔴 顶部「今日一句话结论」—— 市场情绪建议（加仓/减仓/空仓/观望）+ 一句研判
  • 🎯 竞价信号 —— 今天竞价出了什么（涨停梯队 / 一进二 / 连板接力，各最多 3 条）
  • 🔥 涨停池异动 + 板块强度 —— 今日主线
  • 💼 持仓盯盘 —— 有触发条件的票置顶提醒
  • 🗓️ 明日计划 —— 次日作战计划（买谁/价位/验证）

交互：每张卡片可点，跳转到完整面板对应区块（url 锚点），「想看细节再回大面板」。

【可行性】纯新增：加一个 /m 路由 + 一个轻量 HTML；数据复用现有 /api/state（与主面板同源，避免两套口径），或精简一个 /api/mobile-digest。不动任何现有文件。
【风险】需与 index.html 保持同一数据源；新增前端需补守门（jsdom 渲染层 + 移动端断点断言）。
方向 B · 飞书定时「盘面摘要」推送 P0 最高优先级 不打开网页也能看盘

做什么：三个时点各推一份结构化「盘面摘要」到飞书（私密机器人，只有本人）：

时点摘要内容
09:30 开盘后市场情绪一句话 + 竞价信号清单 + 开盘异动
11:30 午休半日小结：主线板块 + 持仓盯盘状态 + 今日已推信号汇总
15:00 收盘全天总结：情绪定论 + 信号命中回看 + 明日计划预告
【可行性】项目已有定时推送机制（定时器 + feishuq.js 队列 + sentToday 幂等），只需新增三个定时摘要任务，复用现有闸门与去重，不新造轮子。
【风险】推送频率上升可能打扰 —— 必须配一个「摘要静默开关」，且严格遵守幂等（同一天同摘要不重发）。
方向 C · 推送升级可交互卡片 P1 锦上添花 精致度提升

做什么：把飞书 msg_type:'text' 升级为 msg_type:'interactive' 消息卡片：红涨绿跌（A股惯例）、字段化布局（现价/距涨停/资金/板块/时间）、带「看详情」按钮跳转线上面板。

【事实·技术边界】飞书 webhook 支持 interactive 卡片，但按钮只能「跳转 URL」，不能做「加持仓」这类需要服务器回调的动作 —— 那要升级成「飞书开放平台应用 + 事件订阅」，是重投入（需申请应用、配回调地址、管 token）。
【风险】飞书卡片字段有字数上限；卡片按钮的「回调型交互」本轮不做（只做 URL 跳转），除非你愿意上开放平台应用。
※ 已有 _cardOf 每票一张卡片的纯文本版，本方向是把它「可视化」成真卡片。

五、为什么这样做

  • 避开雷区：三条全部是「新增」，不碰你「看不习惯」的现有布局。
  • 命中痛点：「信息过载」的解法不是「把更多东西塞进一屏」，而是「把结论抽出来」—— 速览页抽「结论卡片」、定时摘要抽「时点结论」。
  • 优先级理由：A/B 直接解决「找不到重点」，投入小、见效快，故 P0；C 是精致度，且有技术边界，故 P1 暂缓。
  • 工程一致性：复用现有 /api/state、feishuq.js、sentToday，不引入两套口径。

六、具体执行步骤

阶段一（P0）：速览页 + 定时摘要

  • 1. 后端加 /m 路由（或 /api/mobile-digest），聚合「情绪结论 + 竞价信号 + 涨停异动 + 持仓提醒 + 明日计划」。
  • 2. 新增轻量前端 mobile.html（大字、卡片式、红涨绿跌、点击跳转主面板锚点）。
  • 3. 新增三个定时摘要任务（09:30 / 11:30 / 15:00），复用 feishuq + sentToday 幂等。
  • 4. 补守门：_test_mobile_digest.js（jsdom 渲染层 + 断点断言 + 与主面板同源校验）。
  • 5. node --check 全量 + _runall.js 对照基线（红灯 ≤ 基线 7 套件，0 新增红）。
  • 6. 走发布闭环：_publish.py sync → --apply → 部署 → --restore → _post_publish.py。

阶段二（P1）：可交互卡片

  • 1. feishuq.js 支持 interactive 卡片构造（红涨绿跌字段 + URL 跳转按钮）。
  • 2. 逐类信号替换为卡片（先竞价/大单，再持仓提醒）。
  • 3. 补守门 _test_feishu_card.js（卡片结构断言 + 字数上限 + 旧 text 写法反证）。
  • 4. 同上回归 + 发布。

七、关键提醒与风险（请勿忽略）

① 推送频率 vs 打扰：定时摘要会让每日推送从「仅触发时」变成「触发 + 三份定时」，打扰度上升。必须配「摘要静默开关」+ 严格幂等，否则可能变成新的「噪音」。
② 可交互卡片的「加持仓」回调本轮做不了：webhook 是单向的。若你坚持要「点按钮直接加持仓」，需要上飞书开放平台应用（重投入），否则按钮只能是「跳转页面」。
③ 数据同源：速览页必须复用 /api/state，绝不能另写一套聚合口径，否则「速览页说涨、主面板说跌」就是新的「两份实现」铁律违规。
④ 飞书卡片字段长度：卡片有字数上限，超长会截断或发送失败，需在构造层做截断兜底。
⑤ 发布闭环：任何改动都要走 _publish.py 完整闭环，新前端文件要进 CODE_FILES，否则线上看不到。
※ 未验证假设：本方案未实际验证「飞书 webhook interactive 卡片的当前字段规格」——实施阶段一前需先用测试机器人发一张样卡确认（5 分钟成本）。
